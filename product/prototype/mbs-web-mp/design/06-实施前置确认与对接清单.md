# 06 · 实施前置确认、外部对接与 PMS 接口清单

> 用途：把「久窝朋赞会」从设计推进到排期/联调前，必须**提前拍板的决策点、需对接的外部服务、需 PMS 提供的接口能力**一次列清；并给出"评价 / 房东回复评价"的归属与落地方案。

---

## 一、需提前确认的点（决策点）

### A. 业务规则
1. **直订范围**：是否仅限**自营栖舍门店**（不含美团房源）？建议是——美团房态以美团为权威，C 端直订会造成房态双写/超卖。
2. **折扣叠加/互斥**：原型演示"平台会员折 × 门店会员折"相乘（combinedZhe）。需确认：
   - 券 / 随心住 / 储值 与会员折的**叠加或互斥**关系；
   - 是否有**优惠封顶 / 最低成交价**；组合优先级。
3. **成长值规则**：消费 1 元 +1、入住 1 晚 +100、带图点评 +50；**年度 12/31 结算是清零还是保级？** 是否有降级。
4. **积分规则**：平台积分 / 门店积分的获取（离店返积分数额，原型"返 150"）、**消耗场景（能否抵现/兑券）、有效期、过期**；平台与门店积分是否互通（原型：不互通）。
5. **门店会员触发点**：原型"入住或到店关注即自动成为门店会员"——**关注的具体动作是什么**（扫码/定位到店/首次下单/首次入住）？以哪个为准。
6. **门店储值**：**充值入口/充值优惠/可用范围/能否退/能否跨房型**（原型只展示余额，未见充值流程）。
7. **随心住**：**退款规则**（未使用晚数可退否、按比例否）、**延期规则**（是否仅临期无房可延、延几天、可延几次）、能否转赠、是否可叠多张、跨房型但同门店。
8. **礼品卡**：购买/赠送/绑定/核销规则、是否记名、有效期、可用范围（平台通用 vs 指定门店）。
9. **退订/取消政策**：免费取消窗口与扣费规则（直接决定退款状态机与可退金额）。
10. **发票**：预付（随心住/储值）**购买时开还是核销时开**；订单发票"房东确认后开具"——**开票主体**（久窝平台自营 vs 门店）、税率、内容。
11. **实名时机**：C 端**下单即采集身份证** vs 入住前补录；未成年五必须硬闸在 C 端如何呈现与拦截。

### B. 资金与合规（务必先过法务/财务）
12. **预付资金合规**：储值 / 随心住属**预收款**，是否触发**单用途商业预付卡备案 / 资金存管**要求；退款路径与时效。
13. **收款与分账主体**：收款方是**久窝平台统一收款**还是门店/房东？自营通常平台统一收款——是否需要**分账**（微信/支付宝分账）给门店结算？这决定支付接入形态。
14. **资金对账口径**：支付/退款/预付/核销的对账规则与责任方。

### C. 技术/架构（跨系统关键）
15. **用户身份对齐（最关键）**：MBS 的 `c_user` 与 PMS booking 的关联键是什么？
    - 方案：**下单占房时 MBS 把 `order_no` + `c_user.uid` 传给 PMS，PMS 在 booking 上冗余这两个外部引用**；PMS「入住完成事件」再带回它们，MBS 才能精准给对的人加成长值/晚数/积分。
    - 手机号可作辅助锚点，但主锚点用 `order_no`/`uid`，避免手机号变更问题。
16. **事件通道选型**：PMS→MBS「入住完成/取消/改期」事件用什么（MQ / 现有 Centrifugo / HTTP 回调）？投递语义（至少一次 + MBS 侧 `c_inbox_event` 去重）。
17. **门店/房型映射**：`store_id`↔PMS `property_id`、`pms_listing_id`↔PMS 房型 ID 的对齐与同步机制（房源检索快照的刷新方式：事件驱动 or 定时）。
18. **MBS 独立库**的部署/运维归属、备份、与 PMS 的网络与鉴权（沿用 HMAC 签名 + 内网/白名单）。
19. **AI 成本与限额**：LLM 行程生成/问栖解析的**每日限额、缓存、降级**策略（PMS 侧 `ai_quota` 可借鉴）。

### D. 运营/内容
20. POI / 城市内容来源（自维护 `c_poi` vs 三方地图 POI）。
21. 首页运营位 / 周边礼遇 / 灵感目的地 / 随心住广告的**配置归属**（mbs-admin）。

## 四、评价 & 房东回复评价：归属与落地

### 4.1 结论：评价真源放 **MBS**
- 评价是**消费者 UGC**，且要跟"会员积分/成长值（点评 +50）、房源详情展示、内容审核"强绑定，这些都在 MBS。放 MBS 与整体"用户产生数据归 MBS"一致。
- 用 `pms_booking_id` 关联，作为"**住过才能评**"的凭证（`c_review.uk_booking` 唯一）。
- `c_review` 同时冗余 `pms_listing_id`（房型）与 `store_id`（门店）两个维度 —— **既能按房型也能按门店聚合**。

### 4.2 房东回复评价：不必让 PMS 反向调用 MBS（推荐方案 A）
房东在哪回复，决定要不要"PMS 反向调 MBS"。三种方案：

- **方案 A（推荐）：回复入口做在 MBS 域（mbs-admin 商家视图，或 pms-web 内嵌一个"评价管理"页但直接调 mbs-api）。**
  - 房东/门店运营在该界面查看评价、回复，**直接写 MBS `c_review_reply`**。
  - **不需要 PMS 后端反向调用 MBS**——因为回复动作发生在 MBS 侧界面、写 MBS 自己的库。
  - PMS 只需提供"这条 booking/房源属于哪个门店/房东"用于**回复权限校验**（谁能回哪条），以及可选的"有新评价"通知给房东。
- **方案 B：房东在 pms-web 原生管理评价，PMS 后端收到回复后反向调用 MBS 写回 `c_review_reply`。**
  - 这才需要"**PMS 反向调用 MBS**"。可行，但引入 PMS→MBS 反向依赖，增加耦合与鉴权成本。仅当产品坚持"评价管理必须长在 pms-web、且体验完全原生"时才选。
- **方案 C（不推荐）：评价真源放 PMS。** 会把消费者 UGC、内容审核、点评积分等拆到 PMS，破坏"用户数据归 MBS"的边界，且 C 端展示评价又要反向读 PMS，得不偿失。

> 推荐 **A**：评价与回复都在 MBS，回复入口作为 MBS 的一个 B 端界面（房东可从 pms-web 跳转/内嵌进入，但接口是 mbs-api）。**避免 PMS 反向依赖 MBS。** 若组织上要求房东侧一切在 pms-web 且 PMS 持有回复，则退而用 B。

### 4.3 房间详情页评价列表：按什么维度
- **房间/房源详情页**：以**房型(listing)维度**为主展示该房源的评价（原型 room 页即展示本房源 `roomReviews`），可附"门店整体评分"概要。
- **门店主页**：以**门店(store)维度**聚合展示门店评价与评分。
- 因此 `c_review` 同时存 `pms_listing_id` 与 `store_id`，并建 `idx_listing_audit(pms_listing_id, audit_status, created_at)`；门店维度可另建聚合或加 `idx_store`。
- **评分聚合**（房型平均分、门店平均分、点评数）由 MBS 计算，冗余回 `c_listing_snapshot`（房型级）与门店级快照，供列表/详情快速展示。
- 依赖：`store_id`/`pms_listing_id` 与 PMS 对齐（见 §一.17）。

### 4.4 评价链路要点
- 提交评价 → 内容安全审核（微信 msgSecCheck/imgSecCheck）→ 落 `c_review`（+晒图七牛）→ 发点评成长值/积分（幂等）。
- 房东回复 → 写 `c_review_reply`（方案 A 直接写；方案 B 由 PMS 反向调 MBS 写）。
- C 端展示：房源详情按 listing、门店页按 store，含房东回复。

## 五、落地顺序建议（前置项优先级）

1. **先敲死**：直订范围(§A.1)、用户身份对齐(§C.15)、预付资金合规与收款分账(§B.12-13)、PMS 占房接口与入住完成事件(§3.2/3.3)。这四类是**阻塞项**，其余可并行推进。
2. 支付（含是否分账）与内容安全尽早接入（资金 + UGC 合规长尾）。
3. 评价采用**方案 A**，先不引入 PMS→MBS 反向依赖。
