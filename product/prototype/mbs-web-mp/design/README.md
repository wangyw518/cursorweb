# mbs-web-mp 全新 C 端 · 架构与表设计（设计说明书）

> 面向对象：产品 / 后端 / 前端 / 架构评审
> 目标：把 `mbs-web-mp`（全新旅客 C 端小程序）从"BFF 转发工具"升级为**一套自有数据、可独立演进的完整 C 端体系**，并给出功能拆分、工作量、PMS / MBS 职责边界、架构设计与表设计。

## 1. 一句话背景

久窝现有旅客端 `mbs-web`（H5 + 微信小程序 + 支付宝小程序）+ 后端 `mbs-api`（NestJS）本质是一个**"住后服务工具"**：

- 订单来自美团或 PMS 自来客，客人**并不是在这个 App 里下单的**；
- `mbs-api` 是一层很薄的 **BFF**，绝大多数逻辑转发到 PMS 主后端 `services/api`（FastAPI），只对公开接口做 HMAC 签名；
- 客人能做的事：查订单、看入住指南、实名登记、加同住人、自助退房、帮助反馈。

`mbs-web-mp` 是**全新的 C 端**，目标是把它做成**"从种草→下单→入住→履约→复购"的完整消费闭环**，而不是继续做转发。这就要求 C 端**拥有自己的交易域与消费者域数据**，不能再只当 PMS 的门面。

---

## 2. 核心结论先行（回答你最关心的两个问题）

**问题①：C 端要做成完整体系，不只是 BFF 转发——怎么落地？**

把 `mbs-api` 从"薄 BFF"升级为**"消费者域 + 交易域的业务系统"**（有自己的库、自己的领域模型、自己的可靠性设施），只在**供给侧真源**（房源/房态/价格/入住指南配置/合规/门锁）上通过接口读 PMS。即：**读 PMS 的"货架与库存"，但 C 端自己的"人、单、钱、券、评"都自持。**

**问题②：基础配置放 PMS，其他用户产生的数据是否可以全部放 B 端（MBS）？**

**结论：绝大部分"用户产生的数据"可以、而且应该放 MBS；但有两类必须以 PMS 为权威真源，MBS 只持"便捷副本 + 调用凭证"。**

| 数据 | 归属 | 说明 |
|---|---|---|
| 房源 / 房型 / 房间 / 设施 / 价格 / 房态 / 入住指南配置 / 合规规则 / 门锁·未来居 | **PMS（真源）** | 供给侧"基础配置"，C 端只读 |
| C 端账号 / 资料 / 第三方登录 / 收藏 / 足迹 / 搜索历史 | **MBS** | 纯消费者数据 |
| 交易订单 / 支付 / 退款 / 发票 / 购物车 | **MBS（交易域真源）** | C 端自己的"钱与单" |
| 优惠券 / 会员 / 积分 / 成长值 / 活动 / 签到 / 邀请 | **MBS** | C 端营销体系 |
| 评价 / 评分 / 晒图 | **MBS** | 消费者内容 |
| 站内信 / 通知 / 订阅消息 / 反馈 / 客服会话 | **MBS** | C 端触达 |
| 常用入住人 / 我的证件（便捷副本） | **MBS（脱敏/加密）** | 便捷填充；核验与合规真源仍在 PMS |
| ⚠️ 履约/入住单（占房、办入住/退房、房态占用） | **PMS（真源）** | 与房态/公安/门锁/未来居/结算强耦合，必须 PMS 权威 |
| ⚠️ 实名核验结果 / 公安五必须 / HDSP 上报 / 证件照原文 | **PMS（真源）** | 合规与监管口径必须唯一，证件照走七牛私有空间 |

> 一句话：**"人、单(交易)、钱、券、评、信"放 MBS；"货、房态、履约、合规"放 PMS。C 端下单时，MBS 是交易域真源，PMS 是履约域真源，两者通过一次"占房/确认"调用对接（和美团订单进 PMS 是同一套履约模型）。**

这套边界的关键设计是**把"交易订单"和"入住/履约单"拆开**（电商的"交易域 vs 履约域"），详见 [`03-数据归属-PMS-vs-MBS.md`](./03-数据归属-PMS-vs-MBS.md)。
